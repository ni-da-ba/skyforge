# PRES-0005 rendering and art-direction guide

This guide records the accepted **candidate visual language** for Skyforge explanatory graphics. The exact semantic sources remain the Mermaid/source briefs under this directory; rendering may change without changing their claims.

## Visual system

- landscape / 16:9-first composition;
- dark navy project header;
- off-white canvas;
- large numbered sections;
- rounded rectangular information blocks;
- restrained technical palette:
  - blue = authored/world meaning;
  - green = neutral deterministic construction / accepted state;
  - gold = implementation/runtime or active convergence;
  - purple = evidence/human review/roadmap;
  - muted red = communication boundary or explicit caution;
- clear whitespace and no faux terminal/code aesthetic unless code is the subject.

## Five-panel flagship composition

1. **How Skyforge works**
   - semantic descriptors -> versioned recipes -> immutable procedural graph -> deterministic scalar fields -> exact finite 3-D volumes -> runtime backend;
   - evidence is a parallel first-class branch, not an afterthought.

2. **Who owns what**
   - Authorship = world meaning;
   - neutral Skyforge engine = construction + evidence;
   - Implementation = physical realization/lifecycle;
   - Content / Experience = gameplay policy;
   - Presentation = communication;
   - always show that downstream consumption does not transfer authority.

3. **An island is a volume**
   - compare one-Y-per-X/Z heightmap thinking against exact 3-D ownership;
   - show upper surface, interior/caves, underside, and separate vertically stacked volumes;
   - explanatory generated art is permitted only when explicitly labeled **“Explanatory illustration — not a Skyforge runtime screenshot.”**
   - generated/concept imagery must never be used as runtime evidence.

4. **Evidence is part of the architecture**
   - broad/cheap deterministic evidence;
   - representative expensive runtime evidence;
   - human gates only for qualitative questions;
   - screenshots complement rather than replace structural proof.

5. **Current capability vs roadmap**
   - green = accepted now;
   - gold = active convergence;
   - purple = roadmap / strategic;
   - never blend Bootstrap Province or a second backend into the current-capability column.

## Copy discipline

All factual labels must be controlled text derived from current repository authority. Do not rely on image-generation text for:

- milestone/status language;
- technical architecture labels;
- lane ownership;
- runtime capability;
- roadmap wording.

Generated illustration may supply only non-authoritative visual texture.

## Publication-quality threshold

A rendered graphic is ready when:

- its main idea is readable in roughly 10–20 seconds;
- text remains legible at ordinary presentation size;
- no status class is visually ambiguous;
- no generated illustration can reasonably be mistaken for runtime evidence;
- the composition feels coherent with the rest of the set.

Human review is appropriate for this threshold because it is a communication-quality claim rather than a technical producer claim.
