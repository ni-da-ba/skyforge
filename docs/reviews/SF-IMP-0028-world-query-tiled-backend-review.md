# SF-IMP-0028 World Query and Tiled Backend Review

- **Work item:** SF-IMP-0028
- **Review status:** Accepted pending final repository-wide local check
- **Authoritative environment:** local Java 25; hosted GitHub Actions allowance unavailable

## Scope

SF-IMP-0028 establishes the first backend-neutral runtime boundary above the accepted Skyforge island/group/archipelago planning hierarchy.

The accepted path is:

```text
accepted archipelago plan
    -> independent island compilation
    -> bounded world catalog
    -> region/tile query
    -> deterministic density realization
```

No Minecraft classes, block palettes, morphology-family switches, or archipelago-planning calls are present in the backend hot path.

## World-catalog proof

The focused world-catalog verifier passed locally after one contract correction.

Accepted invariants:

- one `SkyIslandWorldVolume` per planned island;
- stable nested runtime identity containing root seed, group identity/ordinal, member ordinal, and geometry seed;
- deterministic plan-order catalog results;
- finite closed `WorldBounds` with exact-boundary inclusion;
- explicit provider-safe vertical reservations rather than inferred provider height bounds;
- empty-sky and vertical-outside queries return no volumes;
- local queries return only conservatively relevant volumes.

### Single-member spacing correction

The first local run exposed a pre-existing validation issue in `SkyIslandGroupRequest`: the request required pairwise center spacing even when a group contained only one member. Since a singleton has no member pair, the constraint had no semantic subject.

The validator now applies the reservation-derived pairwise spacing gate only when `memberCount >= 2`. Multi-member behavior and safety thresholds are unchanged. A focused regression covers the singleton case.

## Tiled backend proof

`ReferenceTiledSkyIslandBackend` consumes only `SkyIslandWorldCatalog` and compiled density graphs.

The local tiled-backend verifier passed and establishes:

- byte-identical monolithic and tiled occupancy;
- identical SHA-256 identity between monolithic and tiled realization;
- identical geometry under different tile dimensions;
- support for irregular partial edge tiles;
- deterministic repeated tiled realization;
- seam-crossing islands remain occupied on both sides of tile boundaries;
- tile ownership is disjoint by global lattice index even when conservative catalog query bounds overlap;
- per-tile catalog culling is active and avoids naive evaluation of every world volume in every tile.

This is the first direct proof that Skyforge geometry can be generated by independently queried chunk-like regions without generation-order dependence or seam loss.

## Architectural interpretation

The proof does not establish that live Minecraft chunk generation will be fast enough. It establishes a more fundamental property: **Skyforge's geometry contract permits live, preloaded, or hybrid realization without changing deterministic world geometry.**

A future backend may therefore choose among:

- direct live region/chunk evaluation;
- preloaded archipelago/region realization;
- hybrid coarse-region caches serving smaller chunk requests.

The policy should be chosen later from measured latency, memory, cache reuse, concurrency, and first-load cost.

## Remaining limitations

SF-IMP-0028 intentionally does not solve:

- material or biome interpretation;
- Minecraft block selection;
- production graph/vector evaluation performance;
- provider-certified exact spatial bounds;
- persistent catalog/cache serialization;
- asynchronous scheduling;
- production spatial indexing;
- final live/preload/hybrid policy.

## Next recommended layer

The next contract should be **backend-neutral terrain interpretation**, not a Minecraft-specific adapter first.

Geometry currently answers approximately `solid / air` through density. A useful backend needs semantic terrain information such as surface, subsurface, underside, exposed cliff, or regional material/biome identity. Those semantics should remain independent of whether the eventual realization target maps them to Minecraft blocks, a voxel exporter, or another renderer.

After that interpretation layer exists, a Minecraft-like reference adapter can translate semantic terrain cells into concrete blocks without contaminating the core geometry and planning APIs.
